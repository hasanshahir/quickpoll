1. Executive Summary

An end-to-end security audit was performed across the local development environment, git configuration, repository source code, and GitHub configuration. Prior to this audit, several critical and high-severity security oversights were present. While functional code existed, fundamental automated guardrails, identity protections, commit verifications, and dependency checks were missing.

This document outlines each threat that was active, why it posed a genuine danger to the developer and repository, and the exact engineering remediations implemented to eliminate the risk.

2. Threat Breakdown & Engineering Fixes

1. Public Personal Email Exposure in Git Metadata

High Threat
The Threat: The global git configuration had user.email set to a personal Gmail address (hasanshahirconnect@gmail.com). Every git commit embeds this email directly into the unencrypted git commit tree. Automated scraping bots continuously crawl public GitHub repositories to harvest developer emails for targeted spear-phishing, credential stuffing attacks, and spam lists.
How It Was Fixed:
  • Configured both global and local git email settings to use GitHub's private anonymized address: 232662623+hasanshahir@users.noreply.github.com.
  • Enabled GitHub's "Keep my email addresses private" and "Block command line pushes that expose my email" options.

2. Unsigned Commits & Author Identity Spoofing

High Threat
The Threat: Commit signing was inactive (commit.gpgsign = false). In Git, the author name and email are arbitrary text fields; any actor can create a malicious commit with git commit --author="Hasan Shahir <...>" and push it to an open-source project. Without cryptographic signatures, collaborators and reviewers cannot distinguish genuine commits from spoofed code.
How It Was Fixed:
  • Generated an ed25519 cryptographic SSH signing key pair (~/.ssh/id_ed25519).
  • Configured Git globally to enforce signing: git config --global gpg.format ssh, git config --global commit.gpgsign true.
  • Registered the public key on GitHub as a Signing Key, unlocking the cryptographic green Verified badge on all authored commits.

3. Accidental Secret & Credential Leakage

Critical Threat
The Threat: There were no pre-commit guardrails to stop sensitive files (e.g. .env, private keys, database connection strings) from being staged and pushed. Automated internet scanners index public GitHub pushes within seconds. Once a secret is pushed, it must be considered compromised—even if deleted in a subsequent commit.
How It Was Fixed:
  • Implemented a local pre-commit hook (scripts/check-secrets.js and .githooks/pre-commit) that parses staged diffs (git diff --cached) and blocks commits containing private keys, AWS tokens, GitHub PATs, OpenAI keys, or database URLs with passwords.
  • Added "prepare": "git config core.hooksPath .githooks" to package.json so all collaborators automatically inherit the hook.
  • Hardened .gitignore to explicitly exclude all .env*, *.key, *.pem, credentials.json, cloud CLI artifacts, and OS temp files.

4. Unmonitored Supply Chain & Package Vulnerabilities

High Threat
The Threat: The application relies on npm packages across the client and server. Open-source dependencies frequently suffer from newly discovered vulnerabilities (CVEs) such as remote code execution, prototype pollution, and denial of service. Without automated monitoring, vulnerable packages remain in production indefinitely.
How It Was Fixed:
  • Created .github/dependabot.yml configured to scan the root, client, and server packages weekly.
  • Dependabot automatically opens pull requests with patch bumps whenever a security vulnerability is identified in an upstream dependency.

5. Absence of CI Pipeline Security Gates

High Threat
The Threat: Without continuous automated scanning on pull requests and pushes, malicious code or credentials could be merged into main without detection, bypassing developer machines that lack local hooks.
How It Was Fixed:
  • Added GitHub Actions workflow .github/workflows/security-scan.yml.
  • Executes Gitleaks (industry-standard secret scanner) against full commit history on every push and PR to main.
  • Executes npm audit to ensure high-severity dependency flaws fail CI builds before merging.

6. Public Disclosure Risk & Missing Security Policy

Medium Threat
The Threat: Without a declared security policy, security researchers or users who find an exploit typically open public GitHub issues, alerting malicious actors before a patch can be developed and deployed.
How It Was Fixed:
  • Added SECURITY.md establishing a private disclosure channel via GitHub Private Vulnerability Reporting and encrypted email.
  • Defined explicit 48-hour response expectations and supported software versions.

7. Application-Level Exploits & Ballot Stuffing

Critical Threat
The Threat: In a zero-login polling system, malicious users can script automated ballot stuffing, perform denial-of-service via massive payloads, or exploit race conditions by firing parallel HTTP requests to register multiple votes.
How It Was Fixed:
  • Atomic Database Constraint: Compound primary key PRIMARY KEY (poll_id, voter_token) in PostgreSQL. Parallel requests trigger code 23505 (unique violation), returning 409 Conflict (verified by 10/10 concurrency tests).
  • HTTP Security Headers: Integrated helmet to protect against MIME sniffing and clickjacking.
  • Rate Limiting & Payload Limits: Strict 10kb body limit, 20 poll creations/hour/IP, and 30 votes/minute/IP.
  • Secure Cookie Flags: Server-issued qp_voter cookie with httpOnly, SameSite=Lax, and Secure in production.
